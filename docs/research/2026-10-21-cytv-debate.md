这不是为了达成一致而让步。改变排序的依据是：

1. 辩论规则明确了“先不动、只留档”和“维护期按 issue 排期”，这比原稿中的扩展方向优先。

3. README 明确写着主页键接管“真电视待实测”，因此当前最直接的缺口是验证既有能力，而不是先搭一套新的交付基础设施。

但我仍不同意用未经验证的用户画像或目录比例，推导“国行收益已经确定很小”，也不接受“只写 prompt 就天然安全、没有维护成本”。以下逐项回应。

### 1. 关于“对国行用户的增量很小”

**表态：部分同意。**

#### 同意的部分

CYTV 的设备资料以海外 Android TV / Google TV 为主；它的典型 `pm disable-user` 路线，不是国行大品牌限制的通用解。

国行安装校验、HOME 白名单、私有启动逻辑等限制，确实使“照抄 CYTV 就扩大大量覆盖”的推断站不住脚。原稿没有足够证据为自建套件预估收益，这一点应收紧。

#### 不同意的部分

**“没有证据证明增量大”，不等于“有证据证明增量很小”。**

这里有三个证据问题：

1. **目录数量不是用户收益的分母。**  
   国行目录少，只说明上游收集的样本少；不能直接推算 UnitedU 目标用户中的可解决比例。我们没有目标用户机型分布、安装失败统计，也没有这些方案在 UnitedU 上的实测转化率。

2. **10 月 2 日研究是有明确局限的历史调查，不是所有品牌永久性的能力定论。**  
   `docs/research/2026-10-02-tv-compatibility.md` 开头明确说，除 A95L 外未做真机验证，部分结论来自低把握度资料。该文还保留了当时“UnitedU 只声明 LEANBACK_LAUNCHER”及 Google TV 只能停原厂桌面的历史描述，不能不区分时间地作为当前能力全集。

3. **CYTV 已提供国行相关的新机制证据，虽然不能直接产品化。**  
   固定快照的[小米 MiTV-AETP0 报告](https://github.com/Gathin23/cleanyourtv/blob/687b5ee/docs/devices/xiaomi-mitv-aetp0-dofus.md)记录：
   - 标准包名不能成为 HOME；
   - 停原厂桌面落到 FallbackHome；
   - 无障碍重定向当前会话有效，但重启后启用记录被删除；
   - 特定允许列表包名的构建报告成功。

   我不支持 UnitedU 冒用这个包名。但这说明，**国行资料的价值不只是“可复制的一条停包命令”，还包括纠正失败原因、识别重启限制、避免错误操作。**

因此我建议共同采用的表述是：

> **目前没有证据支持 CYTV 能显著扩大 UnitedU 的国行覆盖；已知直接适用范围有限，增量尚不能量化。这不足以支持当前建设通用套件，但值得按具体 issue 查询和验证。**

这与“现在不投入”一致，又不把尚未验证的范围过早判死。

### 2. 关于“Agent 安装的用户画像与国行用户错位”

**表态：部分同意。**

#### 同意的部分

电脑、调试授权、模型服务、网络访问和工具使用，都构成额外门槛。对于只想在电视上安装 APK 的普通用户，Agent 不能取代 U 盘、文件管理器或图文教程。

所以我同意：

- 普通 APK 安装是主路径；
- Agent 不应成为必要条件；
- 不值得为了这一渠道重构产品或另发一种 APK。

#### 不同意的部分

“必须使用付费且大陆访问受限的 Claude Code / Codex”和“真正受益者就是海外用户”，都超出了目前证据。

CYTV 固定快照的 [`PROMPT.md`](https://github.com/Gathin23/cleanyourtv/blob/687b5ee/PROMPT.md)写的是：

> “Claude Code **or another coding assistant with shell access**”

技术前提是有 shell 能力的助手，并没有把付费、某一家模型或某个地区服务写成必要条件。可用替代方案的质量与成本还需要验证，但不能把一种典型部署方式当成不可改变的产品要求。

此外，需要区分：

- **电视的使用者**；
- **帮助他安装和维护的人**。

使用者可以是普通家庭成员，操作者可以是已有 Agent 的家人或技术用户。Agent 渠道可能服务的是后者，而不是要求每位电视使用者订阅编程助手。

反过来，我也没有证据证明这个群体足够大。因此正确结论不是“必有市场”，而是：

> **Agent 是针对已有电脑、调试条件和助手使用经验的协助安装者的可选渠道；这个群体在 UnitedU 用户中的规模和实际收益未知。**

“国行用户习惯当贝 / 沙发管家式教程”可以作为产品假设，但 §16 没有提供用户调研或行为数据，暂不能作为否决 Agent 渠道的事实依据。

### 3. 关于“关键未知数是 Level 2，先拿真 Google TV 结果”

**表态：同意，但需要限定结果能说明什么。**

这是 §16 中最能改变近期决策顺序的一点。

证据明确：

- 双语 README 的主页键接管段落都注明：Google TV / Android TV 14 模拟器已验证，真电视未验证。
- 英文 README 已在征集真实 Google TV / GMS Android TV 测试。
- 现有兼容性 issue 模板已经区分“接管后能进 UnitedU”和“接管开不了或不管用”。

所以，**验证已有 Level 2，信息价值高于先建设通用 Setup 工具**。这不要求我们购买设备或立刻组织测试；维护期可等待、响应愿意配合的兼容性报告。

不过需要两条边界：

#### 一台成功，不等于海外问题全部解决

不同 Android 版本、厂商无障碍策略、安装来源限制和遥控器事件可能不同。第一台真机是一个高价值样本，不是 Google TV 全平台认证。

至少要区分：

- 服务能否开启、是否实际绑定；
- 真遥控 HOME 是否有效；
- 待机、屏保、应用返回是否正常；
- 冷启动后是否仍有效；
- 是否出现用户不能接受的副作用。

小米报告中“会话有效、重启失效”正说明只测当场按一次 HOME 不够。

#### 一台失败，也不意味着下一步立即停原厂桌面

应该先区分是授权、服务绑定、按键策略、窗口识别还是持久性问题。只有明确是现有 Level 2 无法合理解决的机制限制，才值得重新评估替代路径。

因此我接受这样的顺序：

> **先在具体 issue 中验证并诊断既有接管能力；成功只扩大到已验证的设备范围，失败先定位原因，不自动升级到 debloat。**

### 4. 关于“倾向 A 的轻量版，而不是 C；debloat 责任不接”

**表态：部分同意；接受当前不建设 C，但不同意只靠 prompt 或上游合作就算完成安全边界。**

#### 我接受的调整

根据维护期约束、现有 issue 收集入口和 Level 2 的真机证据缺口，我接受：

- 当前不建设独立 Setup 核心；
- 不复制 CYTV 的 123 份精简清单；
- 不维护第二套品牌级 debloat 数据库；
- 不因这次研究给 UnitedU 增加系统清理职责；
- 不把原稿阶段 A/B/C 当成已认可路线图。

这意味着原稿“倾向 C”应降为**未来条件选项**，而不是当前推荐行动。

#### 仍需讨论的第一点：“只读诊断 + 安装 + 设 HOME”不是只读流程

只读诊断与后续写操作必须分开命名、分开授权。

安装会改变包状态，覆盖安装可能影响当前实例；`set-home-activity` 会改变偏好；无障碍授权也属于系统状态变化。即使不 debloat，也需要明确：

- 选中哪台设备、哪个用户；
- 安装哪个官方包；
- 是否保留用户数据，禁止擅自卸载或清数据；
- 修改前记录什么；
- 每步怎样验证；
- 失败在哪停止；
- 不允许自动升级成停包、改包名、关校验。

**轻量化应缩小支持范围，而不是删掉这些约束。**

我不坚持先开发全套脚本。人工教程、限定命令的指引或已有工具都可以。但 prompt 只能指导 Agent，不能在技术上保证它不越界；不能宣传为“安全限制已被强制执行”。

#### 仍需讨论的第二点：上游“选择 UnitedU”不是只替换 APK 地址

CYTV 固定快照的 `PROMPT.md` 明确要求：停原厂 Launcher 后，如果 Input、Settings、YouTube 等键失效，用**它自己的** `InputKeyService` / `HomeKeyService` 配置恢复。

研究稿 §4.3 已核查，UnitedU 没有这套同等的任意按键映射。

因此：

```text
保留原 CYTV 流程
→ 只把最后安装的 Launcher 换为 UnitedU
```

可能会去掉原流程依赖的按键修复能力。这不是“debloat 归上游，我们只管 APK”就能解决的接口问题。

我接受**探讨上游合作**，但若未来提出 UnitedU 选项，应有明确分支：

- 官方 UnitedU 包；
- 默认不停原厂组件；
- 不宣称具备 CYTV 自带 Launcher 的按键修复能力；
- 上游清理若已改变系统状态，报告中明确记录；
- 没有对该组合验证，就不称为官方支持组合。

上游不接受这些边界，也不应因此立即启动自建 C。

#### 仍需讨论的第三点：不建设备库，不等于不留 UnitedU 自己的验证证据

我赞成设备精简知识留在上游，但 **UnitedU 的兼容结果必须由我们保留**。CYTV Launcher 在某电视成功，不证明 UnitedU 成功。

目前用已有 compat issue 就够了，不需要新目录、同步器或数据库服务。至少保留型号、地区、固件、UnitedU 版本、安装方式和实际接管结果。

这是一项现有产品的支持记录，不是把自己变成电视改造平台。

### 7. 我补充的产品判断：不要为了“合作”主动承担现在已经可以避开的故障链

上游已有完整 debloat 流程，不代表 UnitedU 接上它就节省维护成本。

原厂桌面被停用后出现的按键、Cast、网络和开机问题，用户会在“UnitedU 安装过程”中遇到；即使技术责任属于外部脚本，支持请求仍可能回到我们这里。前述 `PROMPT.md` 对自带按键修复服务的依赖，就是一个具体例子。

因此“轻量 A”只有在以下定义下才真的轻量：

> **交流与推荐入口可以合作；系统修改能力不自动继承，兼容承诺不互相继承。**

这不是反对合作，而是要求先定义接口，再讨论合作是否省力。

## Claude · 第 1 轮

## 最终方案(草案)

### 一、方案性质与当前状态

本方案是 Pi 与 Claude 对 CYTV 研究的收敛提案，**不是实施授权**。

继续遵守：

- Gordon 已定的“先不动、只留档”；
- UnitedU 1.2.0 后维护期、按 issue 排期；
- 既有真机操作、测试和发布规则。

当前不启动 Agent 套件、独立 Setup 核心、设备数据库、系统精简功能或上游合作 PR，不因本次讨论新增 APK 版本。

### 二、共同产品判断

1. **CYTV 与 UnitedU 技术上互补、用户需求上部分竞争。**  
   CYTV 的主要可借鉴价值是设备知识、安装诊断与系统修改经验，不是要求 UnitedU 替换自己的 UI 架构。

2. **目前没有证据支持结合后能显著扩大 UnitedU 的国行覆盖。**  
   已知直接适用范围有限，新增覆盖不能量化；目录数量、stars 和他人的 Launcher 成功记录都不是 UnitedU 的兼容证明。

3. **Agent 不增加系统权限。**  
   它不能保证突破厂商签名、HOME 白名单、安装器校验或硬编码。安装成功、成为默认 HOME、无障碍接管有效、重启后保持必须分别验证。

4. **Agent 安装只能是可选渠道。**  
   它可能服务已有电脑和助手使用经验的协助安装者，但收益与用户规模未知，不能取代普通侧载路径。

### 三、保持同一个正式 APK

UnitedU 继续使用同一个正式包名、签名和更新体系：

- 不增加“Agent 版”APK；
- 不默认提供冒用白名单包名的兼容构建；
- 不为安装渠道分裂用户数据和发布链；
- 正式 APK 可通过电视允许的浏览器、U 盘、文件管理器、文件传输工具或 ADB 安装。

厂商是否允许安装，与 Android 的“安装未知应用”开关是不同层面的限制。

### 四、文档维护候选

以下仅登记为候选，待获准或进入相应 issue 后处理；用户文档保持双语同步。

#### 1. 纠正首装说明

删除“首次必须 ADB”的错误推论，说明：

- 自带上传页需要 UnitedU 已安装；
- 但其他侧载方式可用于首装；
- 可用渠道取决于具体厂商和固件；
- 安装、默认 HOME 与无障碍接管不是同一步。

#### 2. 收紧原厂桌面停用说明

当前 README 对停用 `launcherx` / `setupwraith` 的说明不能继续被理解为通用推荐步骤。

应明确已知的 Wi-Fi、Cast、遥控按键和开机风险，降为带范围限制的外部高级研究引用；不把它作为 UnitedU 默认安装流程或 Level 2 失败后的自动下一步。

#### 3. 增加小米重启风险的限定提示

引用 CYTV `687b5ee` 的 MiTV-AETP0 / Android 9 / 固件 `22.9.2.851` 报告，说明该设备出现过无障碍重定向启用记录在重启时被移除。

必须标注：

- 外部报告；
- 非 UnitedU 复验；
- 其他型号、固件未知；
- 当场成功不等于冷启动后持续有效。

不据此宣布全部小米设备或 UnitedU 在该设备上必然失败。

### 五、先验证现有 HOME 接管，不先建设工具

在有具体兼容性 issue 和自愿配合的测试者时，优先验证现有 Level 2。

使用已有 compat issue 保存：

- 型号、地区、Android 与固件版本；
- UnitedU 版本和安装方式；
- 原厂组件是否被外部工具修改；
- 无障碍服务能否开启、是否实际绑定；
- 真遥控 HOME、应用返回、屏保和待机表现；
- 冷启动后的保持情况和副作用。

原则：

- 一台成功，只形成对应条件下的兼容证据；
- 一台失败，先定位授权、绑定、按键、窗口或持久性原因；
- 不自动升级到停用原厂组件；
- 不把 ADB 注入 HOME 当成真实遥控器无障碍截键验证。

不为收集这些证据另建设备库。CYTV 档案作为参考，UnitedU 结果由本项目自己保留。

### 六、暂不承担 debloat 产品职责

当前不：

- 导入或镜像 CYTV 精简清单；
- 发布系统包停用配置；
- 承诺恢复任意第三方清理造成的系统故障；
- 把语音、Cast、OTA、厂商后台服务默认判为应关闭的组件。

用户报告涉及外部精简时，可以记录并诊断相关背景，但不因此默认承接整套电视改造和恢复工具的维护。

### 七、未来 Agent 指引的最小边界

只有出现相应实际需求并按维护流程获准，才重新考虑轻量 Agent 指引。

必须明确：

1. 只读诊断与写操作分阶段、分授权。
2. 安装使用可验证来源的官方 APK，确认设备与目标用户。
3. 不擅自卸载、清数据、停原厂包、改包名或关闭安装校验。
4. 写操作有必要的修改前记录、结果验证与失败停止条件。
5. 不从未经审查的网络内容自动生成系统修改命令。
6. Prompt 是指引，不宣称提供强制权限隔离。
7. 不要求先建设完整工具链；若现有教程和有限命令已足够，就不扩大工程范围。

### 八、未来上游合作的边界

当前不向 CYTV 提出 UnitedU 安装选项。

以后若重新考虑：

- 不能只替换 APK，而忽略其自带 Launcher 的按键修复依赖；
- 最小合作分支应保留原厂组件，使用 UnitedU 既有接管路径；
- 不为促成合作而主动新增通用按键映射功能；
- 若原厂组件已被其他流程修改，必须记录并单独验证组合行为；
- 即使未来具备按键映射，也不代表其他系统修改风险已经消除；
- 未经验证，不称为官方支持组合；
- 上游不能接受边界，不自动转向自建完整 C 方案。

**合作入口可以共享，系统修改能力和兼容承诺不能自动互相继承。**

### 九、重启工具建设评估的条件

原稿 C 方案保留为远期条件选项，不作为当前路线图。

只有同时出现以下条件，才重新评估最小工具需求：

- 重复、可复现的安装或接管支持问题；
- 现有文档和人工诊断不能合理解决；
- 有明确维护人；
- 有真实设备验证条件；
- 能说明新增工具比修正文档或既有功能更有收益。

满足条件只是启动评估，不自动批准建设完整安装套件或 debloat 平台。

公共 CI 单独按维护需求评估，不与 CYTV 结合捆绑。

### 十、最终结论

> **当前最有利于 UnitedU 的选择，不是立即融合 CYTV，而是保留其可核查的知识，优先补齐既有产品的真实兼容证据，在不扩张系统修改责任的前提下，由实际需求决定是否增加轻量 Agent 入口。**

这既保留了 AI 辅助安装的机会，也避免维护期因一个技术上有吸引力、收益却未验证的方向而扩张产品边界。

### 一、产品目标：扩大“装得上、回得来、留得住”的范围

UnitedU 已经投入很多精力改善进入桌面以后的体验。当前更值得补的是进入和持续使用它的路径：

1. **装得上**：用户知道自己的电视怎样安装正式 APK。
2. **回得来**：按真实遥控器 HOME 能进入 UnitedU，或者明确知道为什么不能。
3. **留得住**：冷启动、待机和应用更新以后仍能使用，不是当场演示成功。
4. **退得回**：尝试失败不会让用户只能恢复出厂设置。

CYTV 最值得借鉴的是把这几件事组织成一个交付流程，而不是它的全部精简清单。

本次试点应验证两个独立假设：

- **渠道假设**：已有 Agent 的用户或协助安装者，能否因此更顺利地完成安装和诊断？
- **兼容假设**：结合设备知识和有针对性的修复，能否让至少一类原本不清楚如何使用 UnitedU 的设备获得可靠路径？

前者成功不自动证明后者；后者失败也不自动否定前者。

### 二、第一项：立即修正安装入口，并降低兼容性报告门槛

#### 具体做什么

同步修改双语 README 和现有 `.github/ISSUE_TEMPLATE/compat.yml`：

- 普通用户主入口仍是正式 APK，列出电视允许的浏览器、U 盘、文件管理器、手机传输和 ADB 路径。
- 明确自带上传页不能用于安装第一份 UnitedU，但首装并不必须 ADB。
- 分开解释安装、系统默认 HOME、无障碍接管及重启保持。
- 收紧停用 `launcherx` / `setupwraith` 的说明，补足 Wi-Fi、Cast、按键和开机风险，不把它写成常规下一步。
- 加入具体型号、固件限定的小米重启风险引用，注明是外部报告。
- 兼容报告改为询问**实际安装方式**，允许没有 ADB、没有测试 `set-home-activity` 的人提交。
- 明确区分“没测”“失败”“成功”，避免目前功能复选框中“没勾选”含义不清。

#### 证据与收益

现有模板要求回答“adb install 能否成功”，HOME 问题也以执行过 `set-home-activity` 为前提。这会排除一部分通过普通侧载安装的用户，影响我们看到的样本。

这项工作的收益不依赖 Agent 是否成功：减少错误门槛和错误操作，也让后续兼容性研究有更可靠的入口。

#### 成本

预计 **0.5–1 个工程人日**，包括双语核对。不是实测报价。

#### 不做的代价

继续把可安装用户劝退到 ADB；继续收集偏向技术用户的反馈；保留可能被人或 Agent 直接照做的高风险简化说明。

#### 成功标准

让未参与开发的人只按文档回答清楚：

- 我不使用电脑能否尝试安装？
- 安装后为何 HOME 仍回原厂？
- 我可以提交哪些信息，不需要先执行哪些命令？
- 哪些高级操作不是项目推荐的默认路径？

同时审查 README、模板和 Agent 指引，不再出现相互矛盾的步骤。

### 三、第二项：交付可试用的 Agent Setup，而不是先建“大平台”

#### 我的取舍

**不赞成只放一段开放式 prompt，让 Agent 自由探索和修改系统；也不赞成一开始建设多品牌配置引擎、Python ADB 替代实现和完整恢复框架。**

第一版采用：

> 双语 Agent 指引 + 标准 ADB + 少量固定辅助命令 + 正式 UnitedU APK。

不要求用户安装 JDK、Gradle 或编译 UnitedU。CYTV 需要构建自己的桌面，我们没有必要继承这个门槛。

#### 第一版具体范围

建议放在现有仓库中，暂不另起仓库。提供三段明确分离的流程：

**A. 诊断**

- 用户明确指定设备，多个设备时不得猜选。
- 收集型号、固件、Android 版本、当前用户、HOME 候选与解析结果。
- 查询 UnitedU 安装版本、相关权限和服务状态。
- 输出脱敏报告，缺失信息标为未知，不硬套结论。
- 默认不采集完整账号信息、网络配置或全量日志。

**B. 安装**

- 下载或使用用户提供的官方发布 APK。
- 固定官方来源，校验包名、版本及签名；不能把同一来源的 hash 当成独立真实性证明。
- 初装与覆盖更新区分处理；不清数据、不卸载重装、不自动降级。
- 如果已装版本更新或签名不匹配，停止并解释。
- 启动后确认实际前台，而不只相信命令返回成功。

**C. 接管引导与验证**

- 优先系统默认桌面设置，其次使用现有 Home Button Takeover。
- 打开相应系统页，由用户完成授权；第一版不直接覆写整个无障碍服务列表。
- 受限设置单独解释，不自动修改 appops。
- 指导用户按真实遥控器 HOME，记录结果。
- 不把注入 HOME、已写启用设置或已经显示主页，当成完整接管成功。
- 最后生成报告，提示关闭调试并检查结果。

**第一版工具不提供停系统包、改包名、关安装校验和通用远程 shell 接口。**

这只能限制工具自身的操作范围，**不能声称约束了一个拥有任意 shell 权限的 Agent**。更强的约束仍需要宿主权限审批；文档必须诚实说明这一点。

#### 收益

- 形成 Gordon 所认可的“仓库交给 Agent”真实入口，而不是停留在设想。
- 把重复解释与环境差异处理交给 Agent，把关键状态判断做成可测试逻辑。
- 为真人兼容试点提供相同的诊断口径。
- 不分裂 APK、签名、用户数据和更新通道。

#### 成本

预计 **3–5 个工程人日**完成受限第一版及测试。先以现有 macOS 环境验收，再覆盖 Windows；Windows 没有完成端到端验证前就明确标注，而不是口头承诺跨平台。

持续成本是跟踪 ADB 输出差异、权限变化和发布入口，不是零维护。

#### 不做的代价

每位协助安装者继续重复搜资料、解释命令；我们也无法知道 Agent 渠道到底有没有收益。等待自然出现重复 issue，可能得到的只是“用户试了一下就放弃了”，而不是可诊断的证据。

#### 成功标准

第一版至少覆盖以下测试：

- 多设备、离线、未授权时不误操作。
- 重复运行不卸载、不清数据、不降级。
- 安装失败、签名不匹配、网络中断有准确结果。
- HOME 角色、前台、服务启用、实际绑定不混为一谈。
- 无法自动判断时明确请求人工验证。
- 工具没有执行系统包停用。
- 至少一位非作者能够从指引完成真实流程，无需维护者接管其 shell。

**诊断和安装流程可以先完成试用版，不必等所有真机验证结束才让人使用；但不能提前宣传已支持那些机型。**

### 四、第三项：主动组织一个小规模真实设备试点

第一场“有 issue 再测”的做法过于被动。我们现在最缺的是证据，而生成证据本身应该是一项主动工作。

#### 具体做什么

招募 **3–5 位自愿测试者**，优先覆盖三种机制：

1. **国行、可安装但默认 HOME 存疑的电视**，如符合条件的海信或小米设备。
2. **海外 Google TV**，验证原厂高优先级下的现有 Home Button Takeover。
3. **另一个国行限制场景**，例如无障碍重启保持或安装被拒；失败样本也有价值，不为了获得成功率而排除。

A95L 可作标准路径参照，但不能代替 Google TV 或厂商锁定设备。

先用稳定版完成基线。发现需要修复的代码问题后，按仓库规则走正式 Beta；不向 Gordon 电视私下直连装包。测试者自己操作自己的设备并逐项授权。

#### 每台设备的最低记录

- 型号、市场、固件、UnitedU 版本、安装来源。
- 原厂包是否早已被别的工具修改。
- 服务启用和绑定状态。
- 真实 HOME、长按、应用返回、待机和屏保。
- 至少两次正常冷启动后的保持情况；未测到的项目明确留空。
- 设置、输入源和应用专用键是否相较基线发生变化。
- 后续一次正式更新后的状态保持，作为单独验收项。

不把一次重启通过扩大成 OTA 后永久有效。

#### 收益

这不是只证明“能不能用”，还会告诉我们下一笔工程投入该放在哪里：

- 授权说明？
- HOME 键码？
- 窗口兜底？
- 开机时序？
- 厂商删除无障碍启用记录？
- 还是系统权限边界，应用代码确实无解？

#### 成本

预计维护者投入 **2–4 个工程人日**用于准备、协助和分析，另有不可压缩的招募与用户等待时间。并行招募，不能用“等待设备”阻塞安装文档和工具工作。

#### 不做的代价

既有 HOME 接管会继续停留在模拟器证据上；产品兼容说明只能反复引用第三方研究；我们无法区分真实系统限制与自己代码的缺口。

#### 成功标准

- 取得至少三个不同设备条件的完整可追溯报告，至少两个来自国行无 GMS 场景。
- 每个失败都能归入明确机制或具体待查问题，不能统一写“厂商锁定”。
- 获得一个新增的、经过实际验证的可用路径，是产品目标；若没有达到，也必须得出可复用的阻断原因，而不是制造成功结论。
- 招募建议设 **两周检查点**：若未获得足够设备，调整招募渠道或缩小已验证范围，不无限等待，也不虚报完成。

这些是试点交付目标，不是以三个样本推算全市场覆盖率。

### 五、第四项：把试点发现转成小范围兼容修复

我不主张只收报告、不修产品。建议预留 **2–4 个工程人日**，解决试点中最高价值的一个或两个问题。

#### 优先研究的两个方向

**1. 非标准 HOME 键路径**

当前 `HomeKeyService.kt` 直接排除非 `KEYCODE_HOME` 事件；CYTV 的服务则包含 `KEYCODE_ALL_APPS` 路径。

这不证明 UnitedU 在该设备上必然失败，因为窗口兜底可能生效；但它足以成为一个具体测试假设：

> 是否存在按键语义不是 HOME、而现有窗口兜底也不能可靠接回的设备？

如果复现，就为该机制加显式、可关闭的支持，而不是默认把所有设备的 ALL_APPS 都劫持成 HOME。

**2. 标准 TIF 不可用时的厂商输入面板入口**

如果测试者的电视确实没有可用标准输入项，但存在已验证的厂商输入面板 Activity，可以增加有限 fallback，让用户不必为了切 HDMI 返回原厂桌面。

先支持确定组件和设备条件，不做允许任意网络配置下发 Intent 的通用引擎。

#### 收益

这些修复能直接改变用户每天按遥控器的体验，也比“增加一个配置数据库”更容易验证用户价值。

#### 成本与风险

涉及全局按键或输入源就需要防误拦截、失效回退和真实设备验证。新增持久化字段、组件、Beta 回退必须遵守现有向下兼容约束。

预留预算不等于一定实现这两个功能。若试点发现更高价值问题，应替换；如果没有适合的修复，不为花完预算而加功能。

#### 不做的代价

可能出现“安装器准确告诉你为什么不好用，但项目不解决本来能解决的问题”的局面。尤其输入源是国行电视日常功能，不能只因为它属于厂商适配就永久置于产品之外。

#### 成功标准

- 在存在该故障的设备上复现前后差异。
- 基线设备没有按键或输入源回归。
- 关闭新能力能回到原行为。
- 单测 / 模拟器通过，相关真机在正式 Beta 验收。
- 只声明经过验证的型号或机制，不扩张成品牌通用承诺。

### 六、第五项：建立最小证据索引，并尽早试探上游合作

#### 证据索引：做，但不做数据库平台

现有 compat issue 是提交入口，不必替换。新增一个小型、版本化的兼容结果索引，链接到原始报告，列出：

- 型号、固件、UnitedU 版本。
- 安装路径。
- 系统默认 HOME / 无障碍接管 / 重启保持分别是什么结果。
- 外部参考还是 UnitedU 实测。
- 已知问题和恢复方式。

**只收我们实际使用到的上游机制资料和自己的结果，不复制 123 份精简清单。**

预计首次整理 **0.5–1 人日**。收益是用户可以找到答案，Agent 不必每次在 issue 中重新推理。不做的代价是证据虽然收到了，却仍散落在讨论里，无法转化为可见的兼容能力。

成功标准是读者能从索引回到原报告，而且不把外部成功自动转成 UnitedU 支持。

#### 上游合作：先提窄议题，不等功能齐备才沟通

我建议在受限安装流程有可展示结果后，向 CYTV 提一个探索性讨论：

> 是否接受“保留原厂组件、安装正式 UnitedU APK、使用 UnitedU 自有接管路径”的可选流程或文档链接？

明确它不是将现有 debloat 流程最后一行替换成 UnitedU，也不具备 CYTV 自带 Launcher 的按键重映射能力。

预计 **0.5–1 人日**准备和跟进。上游是否接受未知，不作为本项目工作的前置依赖。

不沟通的代价是失去共享测试者、纠正互操作问题和减少重复研究的机会。公开讨论可能吸引支持请求，这是需要接受的实际成本。

成功不以合并 PR 为唯一标准：取得明确接口共识、发现不可合作的具体原因，或招募到组合测试者，都算有效产出。不能只发一句宣传就算完成。

### 七、第六项：用公共 CI 保护新入口，但不顺带重建全部构建体系

新增工具既然让人操作真实电视，就应该让外部贡献能够自动检查：

- 诊断输出解析。
- 多设备拒绝、安装版本判断、失败退出。
- 无 ADB 写操作的模拟测试。
- 报告脱敏、配置合法性。
- 双语指引的关键链接和命令是否一致。

第一轮先做这些不需要电视、不需要正式签名的检查。Android 全量公共 CI 可另行扩展，不阻塞试点。

成本预计 **0.5–1 人日**；若环境改造超出预算，先落工具测试 job，不因为追求完整而全部延后。

不做的代价是 prompt、脚本和兼容解析快速变化时，只靠作者手测把关。成功标准是一次故意引入的危险参数处理或失败误报能让 CI 失败，而不只是 workflow 显示绿色。

### 九、执行顺序与预算边界

建议按以下顺序并行推进：

```text
第一步：修正文档与报告模板；同时招募测试者
    ↓
第二步：完成受限 Agent Setup 和工具测试
    ↓
第三步：非作者试用、真实设备验证、形成结果索引
    ↓
第四步：修复一至两个高价值兼容问题，走正式 Beta 验收
    ↓
第五步：用已有试点结果沟通 CYTV 合作，决定下一轮范围
```

工具 CI 随第二步落地；设备招募和上游沟通不必串行等待。

建议第一轮预算上限是 **约 10–15 个工程人日，不含用户等待时间**，以两到三周作为第一次复盘窗口。这是用于控制范围的估算，不是承诺。超出预算时先删跨平台便利功能和通用抽象，不删关键验证、失败处理和用户授权。

第一轮必须能交出：

1. 正确且可操作的双语安装入口。
2. 可独立试用的 Agent 安装诊断流程。
3. 自动化工具测试。
4. 有明确机制结论的设备报告。
5. 若发现可修故障，对应的修复或明确未修原因。
6. 下一轮是否进入高级系统交接实验的书面决定。

**不以 stars、下载量或“支持所有电视”作为成功指标。**样本这么小，也不该用百分比制造精确感。

### 十、我的开场立场

### 七、E4：可以不封装写操作，但固定检查不能只做到电视状态诊断

**表态：部分同意，并明确我愿意缩减的工具范围。**

我接受：

- 第一版不需要自建 ADB 客户端；
- 不需要完整安装事务引擎；
- 经确认后，`adb install`、设置 HOME 和 appop 解锁可以是 prompt 中的标准命令；
- `doctor.py` 使用 Python 标准库组织诊断，是合理起点。

**我愿意不要求第一版必须有“安装写操作 wrapper”。**

但我不接受把所有安装前后检查留给 Agent 临场理解。固定工具范围至少应包含三个检查面：

1. **设备诊断**：设备、用户、系统、HOME、服务状态。
2. **安装前检查**：官方发布信息、下载 hash、APK 身份和版本、目标设备上的已有版本；任何未知或冲突明确阻止该流程继续。
3. **安装后检查**：实际已装版本、显式启动结果、前台结果与需要人工确认的项目。

这些可以是同一个只读工具的子命令，也可以是小型辅助脚本，**不必执行安装本身**。这样保留 Claude 提议的轻量写操作，又让关键判断有测试覆盖。

#### 为什么坚持这部分

仓库已有两处可靠性约束：

- `scripts/release.sh` 的 `check_signer()` 不只算文件 hash，还验证 APK 签名并固定证书摘要；
- `UpdateChecker.kt` 的 `checkUpdateApk()` 检查包名、版本及签名。

说明项目对“官方包身份”和“版本正确”的要求，原本就不是靠一句下载成功。新增电脑端入口不应把这些判断退回到自然语言自由推断。

#### 必须正视一个依赖问题

我开场同时写了“不要求 JDK / Gradle”和“安装前校验 APK 签名”。这两者**不能未经实现核查就一起保证**：

- Python 标准库能校验文件 SHA-256；
- 不能因此声称已验证 APK v2/v3 签名；
- 现有 `apksigner` 路线涉及 Java / SDK 工具依赖。

所以第一阶段应明确：

- 不要求编译项目，不要求 Gradle；
- 提供可靠签名验证路径，并公开其工具依赖；
- 工具不可用时停止自动安装步骤，允许用户另走普通人工 APK 安装；
- 不自行手写签名验证器，也不把缺少验证悄悄当作成功。

这项依赖会影响渠道便利程度，应算入试点成本，而不是藏起来。

**E4 的待确认建议是：“固定只读工具覆盖诊断、安装前检查、安装后检查；实际写命令可以留在逐项确认的指引中。”**

这比我原开场更轻，但仍不同于“只固定电视诊断、其余交给 Agent”。

### 二、E4：发布流水线的验签可以通过受信清单与文件 hash承接，但不是客户端独立验签

#### 1. 已核实执行顺序，Claude 的核心论据成立

`scripts/release.sh` 实际顺序是：

1. 构建并复制 APK 到发布路径；
2. 用 `aapt2` 读取 APK 的包名、版本和最低 SDK；
3. 校验包名、版本等身份；
4. `check_signer "$APK_DIST"`：
   - 执行 `apksigner verify --print-certs`；
   - 检查签名者数量；
   - 比对固定的正式证书 SHA-256；
   - 失败退出；
5. 对同一个 `$APK_DIST` 计算文件 SHA-256；
6. 将版本、最低 SDK、hash 写入清单；
7. 发布 APK 与清单。

我没有看到这条正常路径在验签与发布之间重新修改 APK 内容。

因此，在**信任官方发布流程和取得的清单**这一前提下，客户端验证下载文件的 SHA-256，可以确认它与发布端已经验签的文件一致。

**我接受不再要求第一版电脑端必须安装 Java / SDK 来独立验签。**这是被实际发布顺序说服后的调整。

推荐表述：

> 客户端验证下载文件与受信官方发布清单一致；APK 的签名与身份由官方发布流程预先检查。此模式不构成客户端独立的证书验签。

这比“签名验证传递完成”更准确地表达了信任前提。

#### 2. 两个清单本来就不会完全相同

脚本先生成 GitHub 清单，随后另外生成 R2 清单：

- GitHub 的 `apkUrl` 指向 GitHub；
- R2 的 `apkUrl` 指向 R2。

所以 A2 的“两渠道 latest.json 一致”不能写成 JSON 全等。

应改为：

> 比较发布身份字段：`versionCode`、`versionName`、`minSdk`、`sha256`；分别检查各渠道 `apkUrl` 的来源约束，不要求 URL 相等。

否则按字面实现会拒绝正常发布。

#### 3. 两个发布渠道不是两个独立信任根

两份清单都来自同一个脚本、同一次发布材料，只是托管位置不同。

双渠道比较能帮助发现：

- 单个渠道内容异常；
- 上传或同步错误；
- 缓存或发布时间差异。

但不能证明发布机器、发布流程或两个渠道共同受影响时仍安全。应称为**双渠道交叉检查**，而不是独立验签或两个独立信任根。

#### 4. 我不赞成把 GitHub 与 R2 同时可达作为默认自动安装前提

这是本轮仍需讨论的实质取舍。

仓库 `gradle.properties` 明确把 R2 放在前面、GitHub 作为后备；`release.sh` 也明确说明 R2 用于国内可达分发，而且：

- GitHub 与 R2 顺序发布，不是原子同步；
- R2 上传是可选步骤，缺配置可以跳过。

草案要求“任一缺失就停止自动安装”，会把两个替代渠道变成共同依赖。对主目标国行用户而言，可能出现：

> 官方 R2 正常、APK 完整可下载，但因 GitHub 不可达，Agent 安装无法继续。

这不是理论上的零成本加固，而是直接改变分发可用性。

**我的建议：**

- 第一版以预先固定的官方 HTTPS 来源作为信任基础；
- 两渠道均可达且可比时做交叉检查；
- **两渠道冲突时停止**，不让 Agent 猜哪份正确；
- 只有一个渠道可达时，如实报告没有完成交叉检查，经明确确认后允许走单渠道模式；
- 不接受任意第三方清单替代官方清单；
- 想获得独立签名验证的人使用公开证书摘要和 `apksigner`。

可以另设“双渠道严格模式”，但不应未经讨论就成为主路径。

#### 5. A2 的身份、签名检查承诺需与实际实现一致

接受发布端检查承接后，Doctor 不必再自行解析 APK 的二进制 Manifest。但报告必须注明：

- 文件 hash：客户端实算；
- 包名与版本身份：基于官方发布流程和清单；
- 设备现有版本：设备查询；
- 已安装包与新包签名是否可兼容：若安装前拿不到可靠证据，就不能伪称已验证。

覆盖安装仍会经过 Android 包管理器签名检查。失败时应停止、保留数据，不能卸载重装。

A2 测试中的“签名冲突”可以验证这一失败路径；不要写成纯 Python 标准库已经能对所有设备提前判定证书兼容。

> 判据不可靠，就只靠第 1 层的显式开关。

问题仍然存在：

1. 用户打开过“重启后自动恢复”；
2. 后来在系统设置里主动关闭无障碍服务；
3. 应用不能识别这是主动关闭；
4. 重启后再次替用户开启。

独立开关表达了某一时刻的授权，但不能自动解释后来相反的操作。

可以设计另一种明确产品语义：

> 开启此功能后，在系统设置关闭服务只会暂时关闭；若要永久关闭，必须先关闭应用内自动恢复。

但这是**新的、需要单独选择的交互与权限语义**，不是上一轮已经接受的“小改”。它也可能让用户认为应用不服从系统开关。

**我建议本轮采用保守的研究闸门：**

> 若无法可靠处理用户主动关闭，不将自动写回作为可发布修复；交付研究结论和人工恢复指引。若仍希望采用“系统关闭只暂时有效”的显式持久化语义，另写方案交 Gordon 决定，不在本次草案中预先批准。

这不会阻止研究，也不会阻止其他候选修复，只是不把安全判据失败变成自动降低要求的理由。

**E6 仍有实质分歧。**
